# Graphr 0.6.0 Immutable Worktree Snapshots Design

## Context

Graphr 0.5.0 starts one server against one checkout, indexes that checkout
before MCP becomes available, and keeps one mutable graph database plus one
in-memory review snapshot. A client can therefore request the right Git base
from a server bound to the wrong checkout and receive a plausible `no changes`
result. Search and view also have no explicit repository or snapshot context.

This is unacceptable when one repository has multiple linked worktrees. Graphr
0.6.0 replaces the implicit current-checkout model with explicit canonical
worktree selection and immutable review snapshots. All ten acceptance tests in
this document are release gates.

## Goals

- Require an explicit canonical worktree root for discovery and indexing.
- Support ordinary and linked Git worktrees without manually reimplementing
  `.git` file, `commondir`, shared-object, shared-ref, HEAD, or index semantics.
- Resolve the requested base and head to exact commit OIDs once and retain those
  OIDs in the snapshot.
- Represent committed, staged, unstaged, untracked, deleted, and renamed
  changes with their exact origin and status.
- Support an unchecked-out commit or branch without creating or changing a
  checkout.
- Make the graph, captured review inputs, deterministic rendered reviews,
  provenance, node references, and pagination cursors belong to one immutable
  snapshot.
- Require `snapshot_id` for every graph-backed MCP query.
- Isolate cache entries by repository, worktree, resolved revisions, selected
  target state, dirty-tree digest, and analyzer/schema version.
- Return explicit structured errors and an explained no-change result. Never
  fall back to another checkout.
- Make indexing asynchronous, observable, cancellable, and concurrent across
  worktrees.
- Reuse unchanged Git-object analysis across linked worktrees.
- Preserve deterministic bounded output, completeness metadata, omission
  reasons, rollback safety, and read-only treatment of Git and worktree state.

## Product Boundaries

- Keep one Rust binary using MCP over stdio.
- Keep Rust and Python as the only indexed source languages.
- Keep Markdown, TSV, and bounded generic text as reviewed artifacts.
- Do not add HTTP, UI, editor integration, embeddings, plugins, migrations, or
  a compatibility layer for the 0.5 server-binding protocol.
- Do not add an arbitrary synthetic merge of unstaged changes without their
  staged base. Git has no canonical state for that combination.
- Do not add automatic cache garbage collection in 0.6.0. Add retention policy
  only after actual cache growth is measured.
- Keep the standalone CLI `index` command as a blocking wrapper around the same
  snapshot builder. It must accept the same explicit root, base, head, target,
  and dependency selection and must not retain separate indexing semantics.

## Architectural Decision

Expose one immutable review snapshot. The request that starts indexing fixes
the worktree root, base, head, target state, untracked inclusion, and dependency
mode. Once complete, that `snapshot_id` is the only context accepted by
`changes`, `search`, and `view`.

The snapshot stores immutable graph data and captured review inputs. `depth`
and `max_nodes` remain bounded rendering parameters for `changes`; changing
them derives another deterministic view of the same captured snapshot and
never rereads Git or the worktree.

This deliberately moves `base` and `head` from `changes` into `index`. Allowing
them to change after indexing would either reinterpret a graph against a new
range or require retaining a second mutable comparison model. Fixing them at
capture time gives one enforceable meaning to snapshot immutability.

The server owns three responsibilities:

1. `AllowedRoots` canonicalizes and authorizes requested worktrees.
2. `JobRegistry` runs independent asynchronous indexing jobs.
3. `SnapshotCatalog` publishes and opens immutable snapshots and reusable graph
   images.

There is no startup `Project`, default checkout, startup index, or global
index/changes mutex.

## Server Configuration and Root Authorization

The public server command is:

```text
graphr serve --allow-root PATH [--allow-root PATH ...]
```

At least one allowed root is required. Each configured path is canonicalized at
startup and must be a directory. A requested `worktree_root` is accepted only
when all of the following hold:

- the input is absolute UTF-8 without control characters;
- its canonical path is equal to or below one configured allowed root;
- Git's canonical `--show-toplevel` result equals the requested canonical path;
- it is a non-bare worktree;
- every Git metadata path used below passes its relationship and file-type
  checks.

Passing a repository subdirectory is an error rather than an implicit root
rewrite. Canonicalization occurs again for every `inspect_root` and `index`
request, so a moved or replaced path cannot inherit prior authorization.

## Linked-Worktree Identity

Graphr delegates worktree interpretation to the installed Git executable. It
runs the following against the canonical requested worktree with the existing
sanitized Git environment:

```text
git rev-parse --path-format=absolute --show-toplevel
git rev-parse --path-format=absolute --absolute-git-dir
git rev-parse --path-format=absolute --git-common-dir
git rev-parse --path-format=absolute --git-path index
git symbolic-ref --quiet --short HEAD
git rev-parse --verify <base>^{commit}
git rev-parse --verify <head>^{commit}
```

Git therefore supplies the correct `.git` file interpretation, per-worktree
Git directory, per-worktree HEAD and index, and common objects and refs. Graphr
canonicalizes and validates the returned paths but does not parse linked
worktree metadata itself.

Identity fields are deterministic hashes of canonical, domain-separated input:

- `repository_id`: canonical common Git directory and Git object format;
- `workspace_id`: `repository_id`, canonical worktree root, and canonical
  worktree-specific Git directory;
- `graph_image_id`: repository identity, exact selected source content,
  language/parse context, and analyzer/schema version;
- `snapshot_id`: graph image, workspace, base/head OIDs, target state,
  dependency mode, captured changes, dirty digest, and review-format version.

Linked worktrees share `repository_id` and the immutable graph-image cache.
They have different `workspace_id` values even when their HEAD OIDs match.

## Typed MCP API

### `inspect_root`

```json
{
  "worktree_root": "/tmp/project-feature",
  "snapshot_id": "optional existing snapshot"
}
```

Without `snapshot_id`, this performs only root authorization, Git identity, HEAD
resolution, branch lookup, and a cheap status summary. It never indexes. With a
snapshot ID, it additionally computes the current selected-state digest and
reports whether the worktree still matches that snapshot.

### `index`

```json
{
  "worktree_root": "/tmp/project-feature",
  "base": "main",
  "head": "HEAD",
  "target": {
    "kind": "worktree",
    "include_untracked": true
  },
  "dependency_mode": "boundary"
}
```

`target` is a tagged enum:

- `{ "kind": "commit" }`
- `{ "kind": "index" }`
- `{ "kind": "worktree", "include_untracked": false | true }`

`commit` may name any resolvable commit or branch and never reads target content
from the checkout. `index` represents the worktree-specific staged state.
`worktree` represents that index plus unstaged tracked content and optional
untracked files. The `index` and `worktree` targets require the resolved
`head_oid` to equal the worktree's current HEAD OID; otherwise Graphr returns
`head_worktree_mismatch`.

The immediate response contains `job_id`, state `queued`, root identity,
requested base/head labels, and their resolved OIDs. Indexing continues in the
background.

### `index_status`

```json
{ "job_id": "job-1" }
```

Returns one of:

```text
queued
capturing
selecting_seed
indexing { files_done, files_total, files_reused }
resolving_graph
publishing
completed { snapshot_id, provenance }
failed { structured_error }
cancelled
```

Job IDs are monotonic and server-local. Completed snapshot IDs are
content-addressed and stable.

### `cancel_index`

```json
{ "job_id": "job-1" }
```

Cancellation is idempotent for an already cancelled job, reports completed
jobs without altering them, and returns `job_not_found` for an unknown ID.

### Snapshot-backed queries

```json
changes({
  "snapshot_id": "<digest>",
  "depth": 6,
  "max_nodes": 50,
  "cursor": "<optional>"
})

search({
  "snapshot_id": "<digest>",
  "query": "AuditRecord",
  "kind": "function",
  "limit": 10
})

view({
  "snapshot_id": "<digest>",
  "node_ref": "<opaque>",
  "depth": 6,
  "max_nodes": 50
})
```

`dependency_mode`, base, head, root, and target state are absent because the
snapshot already fixes them. There is no default snapshot.

The same rule applies to any later caller, callee, flow, or test query: it must
accept `snapshot_id` and may not introduce an implicit workspace context.

Small lifecycle tools return typed structured results. Large search, view, and
changes payloads retain compact bounded text while attaching typed provenance
as MCP structured content.

## Provenance Contract

Every successful snapshot-backed response contains the same provenance object:

```text
repository_id
workspace_id
snapshot_id
common_git_dir
git_dir
repository_root
worktree_root
branch
base_ref
base_oid
head_ref
head_oid
target_state
selected_layers
dirty_digest
commits_base_to_head
changed_files
index_generation
```

`repository_root` and `worktree_root` are both present for API clarity and are
the same canonical Git top-level for a non-bare worktree. `branch` identifies
the worktree's current branch and is absent when that worktree is detached; an
unchecked-out target remains identified by `head_ref` and `head_oid`. Requested
labels are retained for explanation only; all operations use the resolved OIDs.

Paths in compact output use deterministic JSON string escaping. Commit OIDs
support Git's 40- and 64-hex object formats. `dirty_digest` is always a
domain-separated BLAKE3 digest; the commit target hashes an empty dirty overlay
rather than using a sentinel string.

Errors attach all provenance that was safely resolved before the failure.

## Exact Capture Model

One capture produces both the graph input and the review input. Indexing never
re-reads live source files after capture.

### Commit target

- Resolve base and head once.
- Inventory the head tree with `git ls-tree`.
- Read required blobs through one bounded `git cat-file --batch` worker.
- Compare exact OIDs with `git diff <base_oid> <head_oid>`.
- Compute `commits_base_to_head` with the exact resolved OIDs.

This path supports an unchecked-out head and cannot change if a branch label
moves later.

### Index target

- Require `head_oid` to equal the worktree HEAD OID.
- Read the per-worktree index inventory and stage-zero blob OIDs.
- Record unmerged entries as `Unmerged`, omit them from the source graph, emit
  the existing explicit unmerged artifact omission, and keep terminal review
  completeness false.
- Compare base to the captured index with the cached diff path.
- Sample the index inventory before and after capture; reject a mismatch as
  `capture_changed`.

### Worktree target

- Capture the index inventory and staged diff.
- Capture the tracked worktree diff and layer it after the index state.
- Optionally inventory and capture untracked files.
- Copy eligible dirty source and artifact bytes into a unique temporary capture
  using the existing no-follow, canonical-path, stable-metadata checks.
- Stream every selected safe regular dirty file into the dirty digest even when
  its size or encoding makes graph/artifact analysis omit it.
- Hash stable type and metadata records for non-regular omissions.
- Repeat the Git inventory and dirty digest after capture. Reject any mismatch
  as `capture_changed` rather than publishing a mixed snapshot.

The graph builder consumes immutable commit/index blobs and captured dirty
bytes. Snapshot publication persists the captured base-to-target diff,
artifact analysis, path inventory, and layer inventory as review inputs.
Temporary dirty bytes are deleted only after those inputs and the graph image
are atomically published.

## Change Origin and Status

Each changed path retains its final Git status and a sorted set of origin
layers:

```text
committed
staged
unstaged
untracked
```

A path may carry more than one layer. For example, a file committed on the
feature branch and then edited in both the index and worktree has all three of
`committed`, `staged`, and `unstaged`.

Added, modified, deleted, renamed, type-changed, and unmerged remain final path
statuses. Rename records retain both old and new paths. Deletion and rename are
not target-state switches because selectively undoing them would invent a
synthetic tree that Git does not define.

## Immutable Storage and Cache Isolation

Graphr stores versioned manifests and SQLite graph images beneath its existing
namespaced cache directory in the common Git directory. The 0.6 cache namespace
is distinct from the 0.5 mutable database. Graphr does not migrate, open, or
write the old schema.

An index job creates unique temporary manifest, capture, and database paths.
It may copy an immutable seed database, run the existing incremental index
transaction against that private copy, checkpoint it to one complete SQLite
file, validate the final schema/state, and atomically publish it under its
content-derived ID. Published databases are opened only through the read path.

Concurrent jobs never share a writable SQLite file. If two jobs produce the
same final content ID, atomic no-clobber publication keeps the first validated
entry and discards the equivalent temporary result. A corrupt cache entry is
never used as a seed; Graphr rebuilds from the explicit captured target and
reports the rejected cache entry in job status. Failure to produce a validated
replacement returns `cache_corrupt`.

Snapshot manifests bind all of these values:

- repository and workspace identities;
- canonical Git/worktree paths;
- resolved base/head OIDs;
- target state and selected layers;
- dirty digest and captured path inventory;
- graph image, captured review-input, and review-format checksums;
- analyzer, schema, and review-format versions;
- index generation.

The catalog loads only manifests whose worktree remains authorized by the
current server's allowed roots. A snapshot ID is not permission to access a
root that this server was not configured to allow.

## Incremental Reuse

Seed selection is deterministic:

1. Reuse an exact graph-image cache hit.
2. Prefer a same-repository snapshot whose `head_oid` equals the requested
   `base_oid`.
3. Otherwise use the most recent validated same-repository snapshot.
4. Build from an empty graph when no valid seed exists.

The copied graph database already stores path, language, Git blob OID, content
hash, parse context, and byte size. Existing incremental indexing therefore
reuses unchanged entries and reparses only mismatches. Dirty files never reuse
another worktree's analysis unless their full content and parse-context keys
are identical.

Status reports `files_total`, `files_reused`, and `files_parsed`, making reuse
observable without promising a machine-dependent duration.

## Asynchronous Jobs and Concurrency

The MCP `index` call performs only authorization, Git identity discovery, and
base/head resolution synchronously. It registers a job and returns before
capture, parsing, graph resolution, or SQLite publication.

Each job owns:

- immutable request parameters and resolved root/OIDs;
- a cooperative cancellation flag;
- progress stage and file counters;
- unique temporary paths;
- a terminal completion result or structured error.

The existing cancellation checks in Git workers, parser loops, and SQLite
transactions remain the mechanism. Server shutdown cancels active jobs. A
cancelled or failed job removes only its unpublished temporary files and never
changes an older snapshot.

Different `workspace_id` values may index concurrently. One workspace may have
only one active capture. Repeating the identical request returns the existing
job ID; a conflicting request returns `workspace_busy` and that active ID.
Search, view, changes, inspect, and job-status calls do not acquire a global job
lock and remain available while indexing runs.

## Snapshot-Scoped Queries and Cursors

`search` and `view` open the immutable graph database named by `snapshot_id`.
`changes` derives its four sections from that graph database and the persisted
captured review inputs for the requested `depth` and `max_nodes`. The rendered
result is deterministic and may be cached by snapshot ID and those parameters.
These tools never call repository discovery, resolve refs, inspect HEAD, read
the index, or read worktree files.

Node references remain opaque and are validated against both their stored graph
state and the explicit snapshot ID. A node reference from another snapshot
returns `node_snapshot_mismatch`.

Every changes cursor binds:

- snapshot ID;
- section and byte/record offset;
- depth and page-size parameters;
- review checksum and format version.

A cursor used with another snapshot or different original parameters returns
`cursor_snapshot_mismatch` or `cursor_parameters_mismatch`. It never opens the
latest snapshot. Files, diff, artifacts, and graph cursors remain independent,
stable, and exactly reconstructable.

Existing completeness fields, analysis limits, truncation reasons, omission
records, byte boundaries, graph mapping, and terminal review predicate retain
their 0.5 meanings.

## Worktree Divergence After Publication

An immutable snapshot remains queryable after its worktree changes. Queries do
not silently refresh it and do not fail merely because live files diverged.

`inspect_root` with `snapshot_id` compares the current HEAD, per-worktree index,
selected layers, and exact dirty digest with the snapshot provenance. It returns
`snapshot_matches_worktree=false` plus the changed identity fields when they
differ. The client must call `index` explicitly to create a new snapshot. The
old snapshot and all of its cursors remain unchanged.

## No-Change Results

Indexing still publishes a usable graph snapshot when the selected review range
has no changes. `changes` returns typed provenance plus exactly one reason:

- `identical_commit_oids`: commit target and identical base/head OIDs;
- `identical_trees`: distinct commit OIDs whose selected trees have no diff;
- `empty_index_delta`: captured index equals the requested base target;
- `empty_worktree_delta`: captured tracked/untracked worktree target equals the
  requested base target.

The response includes resolved root, base/head OIDs, commit count, target state,
dirty digest, and snapshot ID. A plain unqualified `no changes` string is not a
valid 0.6 response.

## Structured Error Model

MCP failures use a stable machine-readable code, concise human message, and all
validated provenance available at the failure point. Required codes are:

```text
root_unknown
root_disallowed
root_stale
root_not_worktree
git_metadata_invalid
ref_not_found
head_worktree_mismatch
capture_changed
workspace_busy
job_not_found
job_cancelled
snapshot_not_found
snapshot_incomplete
node_snapshot_mismatch
cursor_snapshot_mismatch
cursor_parameters_mismatch
cache_corrupt
```

Unknown roots, refs, jobs, snapshots, or cursors never cause a retry against a
different root. A failed cache seed may be replaced only from the same explicit
captured request. Errors remain bounded and terminal-safe.

## Read-Only and Trust-Boundary Rules

Graphr does not run checkout, switch, reset, update-ref, write-tree, hash-object
with `-w`, or any command that changes Git semantic state. It never writes HEAD,
refs, the worktree-specific index, objects, tracked files, or untracked files.

All repository reads retain the current sanitized environment, no-pager,
no-textconv, output limits, deadlines, cancellation, no-follow opens, canonical
path checks, regular-file checks, and stable metadata checks. Absolute paths
returned by Git are canonicalized and checked before use. Cache writes are
limited to Graphr's versioned namespace under the validated common Git
directory.

## Acceptance Tests

All tests use real temporary Git repositories and real linked worktrees unless
the item explicitly describes a job-registry unit test.

1. **Explicit feature worktree.** Start one server with a main checkout and a
   linked feature worktree allowed. Index the feature root and prove changes and
   symbols come from the feature root, never main.
2. **Complete state representation.** Exercise commit, index, and worktree
   targets across committed, staged, unstaged, untracked, renamed, and deleted
   paths. Assert final status, old/new paths, layer provenance, graph content,
   and artifact coverage.
3. **Concurrent isolation.** Index two linked worktrees concurrently. Assert
   shared repository identity, distinct workspace/snapshot identities, correct
   per-worktree HEAD/index/digest, and no symbol or review leakage.
4. **Post-index edit.** Publish a snapshot, edit its worktree, and prove old
   search, view, changes, and cursor output remain byte-stable. Assert
   `inspect_root` reports divergence and a new index produces a different ID.
5. **Root rejection.** Verify missing, disallowed, replaced, subdirectory, bare,
   and symlink-escape roots return the exact structured errors.
6. **Linked identity.** Assert linked worktrees report the same common Git
   directory and repository ID but distinct worktree roots, Git directories,
   workspace IDs, HEADs, indexes, and dirty digests.
7. **Unchecked-out branch.** Keep main checked out, index another branch in
   commit mode, verify its symbols and changes, and prove HEAD, index, refs,
   objects, and worktree bytes did not change.
8. **Explained empty review.** Compare identical clean OIDs and assert
   `identical_commit_oids` with the canonical root, exact OIDs, zero commit
   count, digest, and snapshot ID.
9. **Non-blocking lifecycle.** Use a controlled blocking worker in a
   job-registry unit test. Prove `index` returns a job before completion,
   progress remains readable, cancellation reaches a terminal state, and an
   existing snapshot remains queryable throughout.
10. **Generic linked-worktree reproduction.** Create a linked feature worktree
    with ten commits and twelve changed files, including `src/replay.rs`. Index
    main first, then the feature snapshot. Assert `commits_base_to_head=10`,
    `changed_files=12`, replay symbols are returned instead of an empty review,
    and unchanged source files are reported as reused.

Additional contract tests prove:

- every snapshot-backed response carries the complete provenance object;
- all MCP root, target, ID, cancellation, and pagination controls are typed;
- node references and cursors reject a different snapshot;
- independent cursor exhaustion reconstructs every section exactly;
- completeness metadata and omission reasons survive cache reuse;
- cache keys change for repository, workspace, OID, target-state, dirty-content,
  analyzer/schema, and review-format changes;
- every operation preserves Git and worktree state byte-for-byte.

## Delivery Sequence

The implementation may land as independently reviewed milestones, but 0.6.0 is
not releasable until all are complete:

1. explicit roots, linked-worktree identity, ref resolution, and provenance;
2. immutable capture, graph images, snapshot-scoped queries, and cursor binding;
3. asynchronous jobs, cancellation, concurrent worktrees, and incremental seed
   reuse;
4. MCP/README/review-skill contract updates, version bump, and the complete
   acceptance suite.

## Release Verification

Before 0.6.0 is considered ready, run:

```text
cargo fmt --check
cargo clippy --all-targets -- -D warnings
cargo test
cargo build --locked --release
```

Also run `git diff --check`, verify the packaged crate from a clean tree, and
exercise every cursor stream against the final binary. Publishing, pushing,
tagging, and external issue updates are outside this design's implementation
phase and require their own explicit release step.
